# 07. Арт-дирекшн и UX

## 1. Главный визуальный принцип

Игра должна выглядеть как современная игра, а не как учебный LMS/дашборд.

Главная ошибка, которой нужно избегать: равнозначные карточки, таблицы, прогресс-бары и панели занимают весь экран и конкурируют за внимание.

Правильная иерархия:

1. **герой-сцена / текущая карта / текущая задача**;
2. **одно главное действие**;
3. **состояние матча**;
4. вторичные режимы;
5. мета-статистика.

## 2. Home screen

Домашний экран должен иметь один сильный фокус.

Варианты:

### A. Синоптическая смена

Большой живой фон/карта текущего сценария и крупная кнопка «Начать смену».

Вторичные элементы:

- ежедневные задания;
- навыки;
- лига;
- достижения.

### B. Центр как база

Центральная иллюстрация/изометрическая база УГМС/АМЦ, где здания соответствуют компетенциям.

Панели только дополняют сцену.

### C. Сезонный сценарий

Как у современных live-service игр: крупный hero-card «Сценарий недели», затем сезонный прогресс и лига.

## 3. Активный матч

Во время матча мета-интерфейс исчезает.

Экран содержит:

- задачу/карту;
- состояние двух игроков;
- таймер, если он методически оправдан;
- OR;
- 3–6 доступных действий;
- минимальные анимации эффекта.

Не показывать:

- достижения;
- магазин;
- общий XP;
- длинные leaderboard;
- рекламные баннеры;
- лишние системные уведомления.

## 4. Карта как сцена

Карта — не маленькая картинка внутри карточки, а полноценная интерактивная поверхность.

Возможности:

- fullscreen;
- включение слоёв;
- плавное масштабирование;
- подсветка станции;
- отрисовка фронта/изобары;
- переключение сроков;
- переключение уровней АТ/ОТ;
- split-view для сопоставления;
- overlay предыдущего срока.

## 5. Визуальные направления

### Направление 1 — Cinematic Operations

- тёмный сине-графитовый интерфейс;
- атмосферная командная/прогностическая сцена;
- реальные карты и спутниковые текстуры;
- акцентный янтарный CTA;
- тонкие светящиеся контуры;
- минимум панелей.

Подходит для основного продукта.

### Направление 2 — Modern Strategy Hub

- упрощённая изометрическая база;
- здания-компетенции;
- лёгкая стратегия прокачки;
- ярче и дружелюбнее;
- подходит для younger cohorts, но не должен становиться игрушечной «фермой».

### Направление 3 — Competitive Seasonal

- hero-сценарий;
- сезон;
- лига;
- battle-pass-подобная визуализация прогресса без monetization pressure;
- тёмный премиальный интерфейс;
- минимальный набор карточек.

### Направление 4 — Character-guided

- стилизованный персонаж-наставник или синоптик;
- персонаж поддерживает повествование, но не закрывает карту;
- подходит для кампании/сюжетных модулей;
- не использовать персонажа как единственный визуальный фокус в профессиональном режиме.

## 6. Что не использовать как основную стилистику

- типичный SaaS dashboard;
- «таблицу успеваемости» как главный экран;
- десятки одинаковых белых карточек;
- декоративную пикселизацию без функциональной причины;
- перегруженный HUD;
- псевдовоенные элементы, если они не относятся к задачам;
- фэнтезийные термины, подменяющие метеорологические.

## 7. Цвет

Цвет должен выполнять три роли:

1. сохранять учебно значимые обозначения;
2. поддерживать игровую иерархию;
3. не смешивать игровые эффекты с метеорологическим кодом.

Поэтому игровой orange/yellow CTA не должен использоваться там, где он может быть принят за цвет учебного слоя карты.

Для метеорологических цветов — отдельные design tokens.

## 8. Типографика

- простой современный grotesk/sans для UI;
- цифры и коды должны хорошо различаться;
- моноширинный/табличный вариант допустим для телеграмм;
- кириллица обязательна;
- минимизировать ALL CAPS в длинных строках;
- на проекторе — крупный кегль и короткие формулировки.

## 9. Анимация

Анимация должна показывать причинно-следственную связь.

Хорошие примеры:

- правильная станция «собирается» в единый символ;
- линия фронта проявляется после анализа;
- OR заполняется импульсом;
- парирование визуально гасит входящий эффект;
- при переключении срока карта показывает направление эволюции.

Плохие примеры:

- бессмысленные частицы;
- длинные победные заставки после каждого ответа;
- тряска карты, мешающая читать данные;
- эффект, меняющий цвет реального фронта.

## 10. Звук

Минимальный набор:

- короткий correct cue;
- error cue без агрессивного наказания;
- combo cue;
- round start/end;
- subtle ambience центра.

Звук отключаем и не используем как единственный канал информации.

## 11. Mobile

Главное правило: **одна задача — один фокус**.

Во время активной задачи:

- compact top bar состояния;
- карта/вопрос занимает основную область;
- ответы в нижней зоне большого пальца;
- нет боковой навигации;
- fullscreen map gesture;
- критические действия подтверждаются только там, где ошибочный tap дорог.

## 12. Desktop

Рекомендуемая структура активного матча:

```text
┌────────────────────────────────────────────┐
│ Player A       Round/Timer       Player B │
├────────────────────────────────────────────┤
│                                            │
│           MAP / TASK / STATION             │
│                                            │
│                                            │
├────────────────────────────────────────────┤
│ tools / answer controls / OR              │
└────────────────────────────────────────────┘
```

## 13. Spectator screen

Это отдельная композиция, а не растянутый player UI.

Показывать крупно:

- имена;
- надёжность;
- текущую карту;
- категорию задания;
- серию;
- результат закрытого вопроса;
- турнирную стадию.

## 14. Instructor screen

Здесь допустима большая плотность данных, потому что задача преподавателя аналитическая.

Но instructor UI не является визуальным эталоном для student UI.

## 15. Вознаграждения

Косметические награды могут быть связаны с метеорологией:

- оформление центра;
- архивные постеры;
- стили рамок профиля;
- значки реальных типов приборов/станций;
- темы карты;
- сезонные эмблемы.

Не давать косметике маскировать или изменять стандартные метеорологические обозначения в учебной задаче.

## 16. База/центр

Если используется изометрическая база, она должна быть семантической:

- радарный пост → радарный блок;
- аэрологическая площадка → аэрология;
- прогностический зал → комплексные сценарии;
- архив → replay и реальные кейсы.

Нельзя создавать здания только ради экономики ресурсов.

## 17. UX ошибок

Ошибка показывается в два этапа:

### В бою

Кратко:

> Неверно — серия сброшена.

### После закрытия задания

Методически:

> Фронт выбран только по температурной границе. Для решения требуется комплекс признаков и согласование с предыдущим сроком/высотными данными.

## 18. UX алгоритмов

Для sequence-задач карточки должны отражать смысл действия, а не только текст:

- иконка предыдущего срока;
- контроль станции;
- цветной карандаш для подъёма;
- изотенденции П/Р;
- фронт;
- финальное оформление.

Это облегчает формирование визуальной памяти, но текст остаётся доступным.

## 19. Design system

Нужны отдельные токены для:

- game UI;
- meteorological semantics;
- status;
- interaction;
- accessibility.

Пример категорий:

```text
--ui-bg-*
--ui-accent-*
--meteo-front-warm
--meteo-front-cold
--meteo-map-lift-precip
--meteo-map-lift-fog
--status-correct
--status-error
```

Учебные цвета нельзя произвольно менять темой оформления.

## 20. Art acceptance criteria

Визуальная концепция принимается, если при 3-секундном взгляде пользователь понимает:

1. что сейчас является главной задачей;
2. где начать игру;
3. кто выигрывает в матче;
4. что является картой/данными, а что — декоративным фоном;
5. какие элементы — профессиональные обозначения, а какие — game UI.
