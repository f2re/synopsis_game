# Развёртывание, релизы и обновления

## Модель релиза
Каждый релиз — самодостаточный `synopsis-game-<version>-linux-x64.tar.gz`: собранный React/Vite-клиент со стилями и Phaser-ресурсами, встроенная рабочая среда Node.js LTS, сервер, шаблоны systemd/Nginx/Apache, установщик и обновлятор. На целевой машине не требуется pnpm/npm и не выполняется сборка исходников.

Каталоги разделены на неизменяемый код и постоянные данные:
- `/opt/synopsis-game/releases/<version>` — неизменяемые релизы;
- `/opt/synopsis-game/current` — атомарная ссылка на активный релиз;
- `/etc/synopsis-game/app.env` — пользовательская конфигурация;
- `/var/lib/synopsis-game` — БД, КН-01, пользовательские данные и резервные копии;
- `/var/log/synopsis-game` — журналы приложения.

Обновление никогда не заменяет `/etc/synopsis-game` и `/var/lib/synopsis-game`. Новые параметры добавляются из `deploy/config/defaults.env`, существующие значения имеют приоритет.

## Astra Linux Special Edition 1.7
Поддерживается x86-64. Установщик использует стандартные `apt`, `systemd`, `nginx`/`apache2`, доступные в ветке Astra Linux 1.7. Node.js не берётся из системного репозитория: проверенный бинарный Node.js LTS включается в релиз, что исключает зависимость от версии Node в ОС.

## Установка
```bash
sudo WEB_SERVER=nginx bash deploy/scripts/install.sh synopsis-game-0.1.0-linux-x64.tar.gz
```
Установщик создаёт системного пользователя, постоянные каталоги, запускает интерактивную настройку, устанавливает выбранный веб-сервер и unit-файлы, применяет миграции, формирует конфигурацию reverse proxy и затем выполняет `/ready` health check.

Для автоматизации можно передать `NON_INTERACTIVE=1` и переменные с теми же именами, что в `defaults.env`.

## Сохраняемая конфигурация
В `app.env` предусмотрены: публичный адрес, доверенные LAN CIDR, провайдер/URL/API key карт, транспорт и endpoint КН-01 (`file|tcp|ws`), версия правил КН-01, БД, режим автообновления. Секреты не включаются в релиз и остаются только в `/etc/synopsis-game`.

## Обновление и откат
`check-update.py` получает latest release GitHub, скачивает архив и SHA-256, после чего `update.py`:
1. проверяет SHA-256 и безопасно распаковывает архив;
2. сохраняет резервную копию конфигурации и данных;
3. добавляет только новые значения конфигурации;
4. выполняет миграции постоянных данных;
5. кладёт новый релиз рядом со старым и атомарно переключает `/opt/synopsis-game/current`;
6. обновляет systemd и конфигурацию Nginx/Apache;
7. перезапускает сервер и проверяет `/ready`;
8. при ошибке возвращает предыдущий релиз и, для локальной SQLite, данные из резервной копии.

Режимы: `UPDATE_MODE=auto`, `notify`, `manual`. По умолчанию предлагается `auto`, а systemd timer проверяет обновления раз в 6 часов с случайной задержкой.

## Данные и миграции
Пользовательские рейтинги, матчи, профили, инвентарь и история должны жить только в постоянной БД под `/var/lib/synopsis-game` либо во внешнем PostgreSQL. Код релиза не содержит изменяемых пользовательских данных. Миграции схемы БД добавляются файлами `NNNN_name.sql|py|sh`; их SHA-256 и факт применения сохраняются отдельно от релиза. Уже применённую миграцию менять запрещено. Перед миграциями сервис останавливается и создаётся резервная копия; при неуспешном health check приложение откатывается на предыдущий релиз, а для локальной SQLite автоматически восстанавливается копия каталога данных. Для PostgreSQL миграции должны быть транзакционными, а политика внешних резервных копий задаётся отдельно.

## CI/CD
PR и push в `main` проверяют структуру, Python/shell, TypeScript, Vite build и server smoke test. Релиз создаётся по тегу `vX.Y.Z` либо вручную через workflow `Выпуск релиза`; workflow повторяет проверки, собирает самодостаточный архив, проверяет его запуск и публикует архив + `.sha256` в GitHub Releases.

Для закрытых/изолированных сетей поддерживается `UPDATE_SOURCE=directory`: новые релизы можно складывать в локальный каталог `UPDATE_DIRECTORY`, без доступа сервера к GitHub.
