# Развёртывание, релизы и обновления

## 1. Что считается релизом

Каждый релиз — самодостаточный `synopsis-game-<version>-linux-x64.tar.gz`. В него входят:

- собранный React/Vite-клиент со всеми стилями и Phaser-ресурсами;
- сервер;
- встроенная рабочая среда Node.js LTS;
- шаблоны systemd, Nginx и Apache;
- установщик, обновлятор, миграции и средства проверки;
- `VERSION` и `manifest.json` с SHA-256 всех файлов.

На целевой машине не требуются pnpm/npm и сборка исходников.

## 2. Постоянные и заменяемые каталоги

```text
/opt/synopsis-game/releases/<version>   неизменяемые версии приложения
/opt/synopsis-game/current              ссылка на активную версию
/etc/synopsis-game/app.env              локальная конфигурация и секреты
/var/lib/synopsis-game/data             SQLite и пользовательские данные
/var/lib/synopsis-game/kn01             локальный приём КН-01
/var/lib/synopsis-game/migrations       журнал применённых миграций
/var/lib/synopsis-game/backups          резервные копии перед обновлением
/var/log/synopsis-game                  журналы
```

Релизный архив никогда не содержит изменяемую рабочую БД, рейтинги, историю игр или локальные секреты. Поэтому новая версия физически не заменяет пользовательские данные при распаковке.

## 3. Astra Linux Special Edition 1.7

Целевая архитектура — x86-64. Установщик использует стандартные `apt`, `systemd`, `nginx`/`apache2`, Python 3 и системные утилиты. Node.js из репозитория ОС не используется: проверенная версия Node.js LTS включается внутрь релиза.

CI дополнительно запускает конечный архив в официальном UBI-образе Astra Linux 1.7 и проверяет:

- синтаксис Python-скриптов на Python ветки 1.7;
- shell-скрипты;
- запуск вложенного Node.js;
- запуск серверного процесса;
- ответ `/ready`.

## 4. Первая установка

Рядом с архивом рекомендуется хранить опубликованный `.sha256`:

```text
synopsis-game-0.1.0-linux-x64.tar.gz
synopsis-game-0.1.0-linux-x64.tar.gz.sha256
```

Запуск:

```bash
sudo bash deploy/scripts/install.sh synopsis-game-0.1.0-linux-x64.tar.gz
```

Установщик:

1. проверяет SHA-256, если файл `.sha256` находится рядом;
2. создаёт системного пользователя `synopsis-game`;
3. создаёт постоянные каталоги;
4. безопасно распаковывает релиз;
5. запускает мастер настройки;
6. устанавливает выбранный Nginx/Apache и, при необходимости, клиент PostgreSQL;
7. применяет начальные миграции;
8. формирует конфигурацию веб-сервера;
9. устанавливает systemd units;
10. запускает приложение и проверяет `/ready`.

Для полностью автоматической установки используется `NON_INTERACTIVE=1`; значения передаются переменными окружения с именами из `deploy/config/defaults.env`.

## 5. Мастер конфигурации

Постоянный файл `/etc/synopsis-game/app.env` содержит, в частности:

- `PUBLIC_URL`, `API_PORT`;
- `WEB_SERVER=nginx|apache|none`;
- `ACCESS_MODE=lan|public`;
- `TRUSTED_LAN_CIDRS`;
- параметры онлайн-карт и секретный API key;
- `KN01_TRANSPORT=file|tcp|ws`, endpoint, правила КН-01, TLS и токен источника;
- `DATABASE_KIND=sqlite|postgres` и `DATABASE_URL`;
- режим и источник обновлений;
- число сохраняемых резервных копий и релизов.

Секретные значения вводятся без отображения в терминале. Файл имеет права `0640`, владелец `root`, группа `synopsis-game`.

## 6. Доступ по LAN

При `ACCESS_MODE=lan` список `TRUSTED_LAN_CIDRS` реально преобразуется в правила доступа:

- Nginx: `allow ...; deny all;`;
- Apache: `Require ip ...`.

Например:

```text
ACCESS_MODE=lan
TRUSTED_LAN_CIDRS=127.0.0.1/32,192.168.10.0/24,10.20.0.0/16
```

CIDR проверяются стандартным модулем `ipaddress`; ошибочная сеть блокирует применение конфигурации.

`ACCESS_MODE=public` снимает ограничение по CIDR. Защита приложенческих ролей и аутентификация при этом остаются обязательными на сервере.

## 7. Nginx и Apache

Приложение может использовать:

- `WEB_SERVER=nginx`;
- `WEB_SERVER=apache`;
- `WEB_SERVER=none`, если обратный прокси управляется внешней инфраструктурой.

`WEB_SERVER_EXCLUSIVE=1` означает выделенный сервер для приложения: установщик имеет право отключить стандартный сайт выбранного веб-сервера и конфликтующий второй веб-сервер. При `0` существующие сайты не отключаются.

Маршруты `/api/` и `/ws/` проксируются на локальный сервер, остальные URL обслуживаются как SPA, поэтому `/arena-tv` и внутренние маршруты работают после прямого открытия в браузере.

## 8. Умное объединение настроек

При обновлении новая версия `defaults.env` объединяется с существующим `app.env` по правилу:

1. уже настроенное значение пользователя сохраняется;
2. отсутствующий новый параметр добавляется из defaults;
3. локальные неизвестные параметры не удаляются;
4. `CONFIG_SCHEMA_VERSION` повышается до версии схемы нового релиза;
5. переход на более старую схему конфигурации блокируется.

Таким образом API keys, адреса карт, LAN CIDR, настройки КН-01, соединения с БД и локальные параметры не стираются.

## 9. Обновление

`check-update.py` поддерживает:

```text
UPDATE_MODE=auto      скачать и применить
UPDATE_MODE=notify    только сообщить о новой версии
UPDATE_MODE=manual    автоматическую проверку не выполнять
```

Источники:

```text
UPDATE_SOURCE=github
UPDATE_REPOSITORY=f2re/synopsis_game
```

или для изолированной сети:

```text
UPDATE_SOURCE=directory
UPDATE_DIRECTORY=/srv/synopsis-game/releases
```

Во втором случае администратор или локальная система доставки просто помещает новый `.tar.gz` и `.sha256` в каталог. Интернет-доступ сервера не требуется.

systemd timer выполняет проверку периодически. Одновременный запуск двух обновлений блокируется файловой блокировкой.

## 10. Последовательность безопасного обновления

`update.py` выполняет:

1. проверку SHA-256;
2. защиту от небезопасных путей и ссылок внутри архива;
3. установку новой версии рядом со старой;
4. остановку приложения;
5. обязательное резервное копирование;
6. объединение конфигурации;
7. миграции БД и данных;
8. атомарное переключение `/opt/synopsis-game/current`;
9. обновление systemd units;
10. повторную генерацию Nginx/Apache из сохранённых настроек;
11. запуск сервера;
12. проверку `/ready`;
13. очистку старых релизов сверх `RELEASE_KEEP`.

Если любой критический шаг завершается ошибкой, используется предыдущий релиз.

## 11. SQLite

По умолчанию:

```text
DATABASE_KIND=sqlite
DATABASE_URL=file:/var/lib/synopsis-game/data/synopsis.sqlite3
```

Перед обновлением каталог данных копируется. При неуспешном запуске новой версии автоматически восстанавливаются:

- старая версия приложения;
- старая конфигурация;
- SQLite-данные;
- журнал применённых миграций.

Это обеспечивает полный автоматический откат локальной установки.

## 12. PostgreSQL

При `DATABASE_KIND=postgres` первичная установка добавляет системный клиент PostgreSQL. Перед каждой миграцией обязателен успешный `pg_dump` в формате custom. Если `pg_dump` отсутствует или завершается ошибкой, обновление не начинается.

SQL-миграции запускаются одной транзакцией. Для PostgreSQL применяется принцип расширения с последующим сжатием схемы: новый релиз не должен сразу удалять поле или таблицу, необходимые предыдущему релизу. Это позволяет автоматически откатить код без немедленного восстановления всей внешней БД.

Дамп сохраняется для аварийного восстановления средствами PostgreSQL. Автоматический `pg_restore --clean` намеренно не выполняется, поскольку внешняя БД может обслуживаться отдельной политикой резервирования.

## 13. Миграции

Файлы:

```text
deploy/migrations/0001_name.sql
deploy/migrations/0002_name.py
deploy/migrations/0003_name.sh
```

Применяются строго по имени. Для каждого файла сохраняется SHA-256. Уже применённый файл нельзя переписать под тем же именем: обновление остановится. Исправление оформляется новой миграцией.

## 14. Резервные копии и старые версии

`BACKUP_KEEP` задаёт число локальных резервных копий, `RELEASE_KEEP` — число установленных версий приложения. Активный и непосредственно предыдущий релиз не удаляются в момент успешного обновления.

Резервная копия содержит конфигурацию, SQLite-данные, журнал миграций и, при PostgreSQL, `postgres.dump`.

## 15. CI/CD и выпуск

Каждый PR и push в `main` проверяют:

- структуру и документацию;
- архитектурные инварианты;
- инфраструктурные инварианты;
- объединение конфигурации и защиту распаковки;
- shell/Python;
- TypeScript;
- Vite build;
- серверный `/ready`/`/health`;
- сборку конечного Linux-архива;
- SHA-256 manifest;
- запуск конечного архива;
- совместимость конечного архива с Astra Linux 1.7.

Релиз создаётся по тегу `vX.Y.Z` или ручным запуском сценария `Выпуск релиза`. До публикации повторяются те же проверки. В GitHub Release загружаются архив и `.sha256`.

## 16. Ручной откат

Автоматический откат является основным механизмом. Для аварийной ручной операции можно выбрать уже установленный каталог:

```bash
sudo ln -sfn /opt/synopsis-game/releases/0.1.0 /opt/synopsis-game/current
sudo systemctl daemon-reload
sudo systemctl restart synopsis-game
```

После ручного отката следует повторно сформировать конфигурацию веб-сервера:

```bash
sudo bash /opt/synopsis-game/current/deploy/scripts/render-web-config.sh
```

## 17. Что не перезаписывает обновлятор

Обновлятор не должен удалять или заменять без миграции:

- пользовательские рейтинги;
- историю матчей и попыток;
- профили и инвентарь;
- содержимое рабочих БД;
- локальные КН-01;
- API keys;
- токены источников;
- LAN CIDR;
- адреса карт и внешних сервисов;
- корпоративные TLS-сертификаты;
- внешние правила резервного копирования.

Это является обязательным инвариантом релизной системы.
