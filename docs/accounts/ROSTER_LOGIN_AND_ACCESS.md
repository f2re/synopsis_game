# Roster Login & Access — закрытый список пользователей и упрощённый вход

**Статус:** accepted-concept

## 1. Принцип

В системе **нет публичной саморегистрации**.

Пользователь появляется только после действия администратора:

- ручное создание;
- импорт CSV/JSON;
- импорт из внутренней системы учреждения;
- заранее подготовленный roster.

## 2. Роли

Минимум:

- `student`;
- `instructor`;
- `content_author`;
- `method_reviewer`;
- `display`;
- `admin`.

Права всегда проверяются сервером.

## 3. Classroom login flow

Цель — вход за несколько секунд без сложного пароля.

Базовый сценарий:

1. игрок открывает игру;
2. выбирает свою группу/курс;
3. выбирает себя из разрешённого списка;
4. вводит короткий персональный classroom code/PIN;
5. получает игровую сессию;
6. сразу попадает в свой хаб.

## 4. Короткий код

В локальной доверенной аудитории допускается очень короткий код, например 1–2 цифры/символа, **но это не полноценный интернет-пароль**.

Такой режим допустим только если одновременно действуют:

- закрытый roster;
- локальная/доверенная сеть или физически контролируемая аудитория;
- rate limit;
- задержка после серии ошибок;
- блокировка перебора;
- audit log;
- отсутствие чувствительных административных функций у student session.

Для публичного интернет-доступа профиль безопасности должен требовать:

- более длинный PIN, например 4–6 цифр; или
- device pairing; или
- institution SSO в будущем.

## 5. Login code не хранится в открытом виде

На сервере хранится verifier/hash, а не исходный код.

Администратор может:

- сбросить код;
- временно отключить пользователя;
- завершить все сессии;
- назначить новый код.

## 6. Защита от выбора чужого профиля

Меры:

- индивидуальный code/PIN;
- rate limit per device/IP/profile;
- progressive delay;
- temporary lock;
- audit события неуспешного входа;
- отображение последнего входа/активного устройства в admin UI.

## 7. Device convenience

После успешного входа доверенное устройство может получить короткоживущий device token, чтобы игрок не вводил PIN при каждом переходе между экранами.

Опционально:

- «запомнить на этом компьютере до конца занятия»;
- QR/device pairing для школьных мероприятий;
- kiosk stations с выбором пользователя при каждой смене.

## 8. Admin roster

Поля пользователя:

```text
user_id
status
display_name
group_id
roles
login_code_verifier
avatar_profile
created_at
disabled_at
```

Дополнительные персональные поля не собирать без необходимости.

## 9. Import

Поддержать:

```csv
external_id,display_name,group,role,initial_code
...
```

После импорта система:

- валидирует уникальность;
- создаёт пользователей;
- выдаёт отчёт по конфликтам;
- не открывает публичную регистрацию.

## 10. Guest / school demonstration

Для школьного дня открытых дверей возможны заранее созданные temporary profiles:

```text
Гость-01
Гость-02
...
```

Они:

- имеют ограниченный срок жизни;
- не могут менять roster;
- не видят приватные данные;
- могут играть demo/Blitz;
- очищаются/архивируются после мероприятия.

## 11. Персонализация после первого входа

При первом входе игрок проходит короткий avatar setup:

1. внешний вид;
2. причёска;
3. стартовый стиль одежды;
4. ник/display preference, если разрешено администратором;
5. выбор стартового фонового companion из разрешённых базовых вариантов.

## 12. Privacy by design

Для игры достаточно:

- display name;
- группа;
- результаты;
- avatar/cosmetics;
- игровые события.

Email/телефон не должны быть обязательны для student account.

## 13. Acceptance criteria

- [ ] саморегистрация отсутствует;
- [ ] пользователь создаётся только администратором/import pipeline;
- [ ] вход занимает несколько секунд;
- [ ] короткий code/PIN не хранится plaintext;
- [ ] есть rate limiting и lockout;
- [ ] student не получает admin privileges;
- [ ] display role не имеет доступа к приватным данным;
- [ ] roster можно импортировать пачкой;
- [ ] account disable немедленно запрещает новый вход;
- [ ] classroom security profile и public-internet profile различаются.
