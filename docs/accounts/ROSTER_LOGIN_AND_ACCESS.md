# Закрытый список пользователей и упрощённый вход

**Статус:** принятая концепция

## 1. Основной принцип

В системе **нет публичной саморегистрации**.

Пользователь появляется только после действия администратора:

- ручного создания;
- импорта CSV/JSON;
- импорта из внутренней системы учреждения;
- загрузки заранее подготовленного списка.

## 2. Роли

Минимальный набор технических ролей:

- `student` — студент;
- `instructor` — преподаватель;
- `content_author` — автор учебного содержания;
- `method_reviewer` — методический проверяющий;
- `display` — автономный большой экран;
- `admin` — администратор.

Имена ролей сохраняются как программные идентификаторы. Права всегда проверяются сервером.

## 3. Сценарий входа в аудитории

Цель — войти за несколько секунд без сложного пароля.

Базовая последовательность:

1. игрок открывает игру;
2. выбирает свою группу или курс;
3. выбирает себя из разрешённого списка;
4. вводит короткий персональный код;
5. получает игровую сессию;
6. сразу попадает в свой «Синоптический центр».

## 4. Короткий код

В локальной доверенной аудитории допускается очень короткий код, например 1–2 цифры или символа, **но это не полноценный пароль для открытого Интернета**.

Такой режим допустим только если одновременно действуют:

- закрытый список пользователей;
- локальная или доверенная сеть либо физически контролируемая аудитория;
- ограничение числа попыток;
- задержка после серии ошибок;
- временная блокировка перебора;
- журнал событий входа;
- отсутствие чувствительных административных функций у студенческой сессии.

Для публичного интернет-доступа профиль безопасности должен требовать:

- более длинный код, например 4–6 цифр; или
- привязку устройства; или
- единую систему входа учреждения в будущем.

## 5. Код входа не хранится открытым текстом

На сервере хранится проверочное значение или криптографический хэш, а не исходный код.

Администратор может:

- сбросить код;
- временно отключить пользователя;
- завершить все активные сессии;
- назначить новый код.

## 6. Защита от входа в чужой профиль

Используются:

- индивидуальный код;
- ограничение числа попыток на устройство, адрес и профиль;
- нарастающая задержка после ошибок;
- временная блокировка;
- запись неуспешных входов в журнал;
- отображение последнего входа и активного устройства в административном интерфейсе.

## 7. Упрощение повторного входа на доверенном устройстве

После успешной авторизации доверенное устройство может получить короткоживущий технический токен, чтобы игрок не вводил код при каждом переходе между экранами.

Допустимые варианты:

- «запомнить на этом компьютере до конца занятия»;
- QR-код или привязка устройства для школьных мероприятий;
- стационарные терминалы с выбором пользователя при каждой смене.

## 8. Структура записи пользователя

Пример технических полей:

```text
user_id
status
display_name
group_id
roles
login_code_verifier
avatar_profile
created_at
disabled_at
```

Имена полей не переводятся, так как входят в программную схему. Дополнительные персональные данные не собираются без необходимости.

## 9. Импорт списка

Поддерживается формат вида:

```csv
external_id,display_name,group,role,initial_code
...
```

После импорта система:

- проверяет уникальность;
- создаёт пользователей;
- формирует отчёт по конфликтам;
- не включает публичную регистрацию.

## 10. Гостевой режим для школьных мероприятий

Для дня открытых дверей можно заранее создать временные профили:

```text
Гость-01
Гость-02
...
```

Они:

- имеют ограниченный срок действия;
- не могут изменять список пользователей;
- не видят приватные данные;
- могут играть в демонстрационные режимы и блиц;
- очищаются или архивируются после мероприятия.

## 11. Настройка персонажа после первого входа

При первом входе игрок проходит короткую настройку:

1. внешний вид;
2. причёска;
3. стартовый стиль одежды;
4. отображаемое имя или игровой псевдоним, если это разрешено администратором;
5. выбор стартового спутника из базовых вариантов.

## 12. Приватность по умолчанию

Для игры достаточно:

- отображаемого имени;
- группы;
- результатов;
- профиля персонажа и предметов оформления;
- игровых событий.

Адрес электронной почты и телефон не должны быть обязательными для студенческой учётной записи.

## 13. Критерии готовности

- [ ] саморегистрация отсутствует;
- [ ] пользователь создаётся только администратором или импортом списка;
- [ ] вход занимает несколько секунд;
- [ ] короткий код не хранится открытым текстом;
- [ ] есть ограничение попыток и временная блокировка;
- [ ] студент не получает административные права;
- [ ] роль `display` не имеет доступа к приватным данным;
- [ ] список можно импортировать сразу для группы;
- [ ] отключение учётной записи немедленно запрещает новый вход;
- [ ] профиль безопасности локальной аудитории отличается от профиля открытого интернет-доступа.
