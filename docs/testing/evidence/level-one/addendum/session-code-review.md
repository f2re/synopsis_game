# Дополнение: неверный текущий код и действующая сессия

**Дата:** 21 ноября 2026 года. **Проверяющий:** `/root/level_security_review`, роль `security-privacy-reviewer`. **Задача:** `LEVEL-ONE-PLAYABLE`.

**Заключение: `PASS` для узкого исправления обработки 401 в клиенте.** Ошибка текущего кода больше не закрывает действительную сессию. Реальное отклонение сессии сохраняет прежнее восстановление входа. Продуктовый код проверяющим не изменялся; [первый отчёт](../security-review.md) оставлен без правок.

## Основание и причина

Отдельный проверяющий автоматических запусков сообщил об остановке [второго запуска PR № 133](https://github.com/f2re/synopsis_game/actions/runs/44937341253) на версии `a4aeb89d257fddbb1ef0be4361c4b46c61d62c85`: сценарий администратора ожидал сообщение «Неверный текущий код» после 401 в `tools/test_admin_screens_browser.cjs`. Данное дополнение проверяет причину и исправление внутри процесса; оно не присваивает себе результаты браузерной проверки.

Причина независимо подтверждена по настоящему [IdentityService](../../../../../apps/server/src/modules/identity/identityService.ts). `setUserCode` сначала проверяет токен, затем сравнивает текущий код. Неверный текущий код возвращает `401 / invalid_code`, но не отзывает сессию и не меняет сохранённый код. Недействительный или истёкший токен возвращает `401 / invalid_session`; отсутствие заголовка авторизации в [маршрутизаторе](../../../../../apps/server/src/index.ts) использует `401 / session_required`.

Предыдущая клиентская обработка считала любой 401 доказательством истечения. Поэтому ошибка отдельной операции очищала токен и вызывала сброс пользователя в `App`. Предыдущий проверочный сценарий использовал условное имя `session_expired` и не покрывал неверный текущий код; это была конкретная граница прежней проверки.

## Проверенное исправление

В [api.ts](../../../../../apps/web/src/api.ts) очистка происходит только при одновременном выполнении всех условий: статус 401, точный код `invalid_session` либо `session_required`, запрос отправлен с токеном, и этот токен по-прежнему текущий. Сравнение выполняется после асинхронного чтения ответа. Событие истечения отправляется после очистки, без дополнительных данных.

| Ответ или ситуация | Проверенный результат |
|---|---|
| Настоящий `setUserCode` отклоняет неверный текущий код | Клиент получает `invalid_code`, сохраняет токен, не отправляет событие истечения; сервер продолжает принимать тот же токен и прежний код входа |
| Правильное повторение смены кода после отказа | Успешно выполняется в той же сессии |
| Настоящий сервис отклоняет отозванный тестовый токен | Возвращает `invalid_session`; клиент очищает соответствующую сессию |
| 401 с любым из двух допустимых кодов сессии | Очищает только совпадающий текущий токен |
| Ответ старого запроса приходит после новой сессии | Новая сессия сохраняется для обоих кодов; отдельно проверена замена токена во время чтения JSON |
| 401 без кода, с `session_expired` или другим неизвестным кодом | Остаётся ошибкой операции, токен сохраняется |
| 403, ошибочный вход пользователя или администратора | Не создаёт события истечения другой действующей сессии |
| Токена нет до вызова | Запрос отклоняется до транспорта, событие истечения не выдумывается |

Существующая форма смены кода передаёт `ApiError.message` в своё сообщение об ошибке. После устранения лишнего события закрытие формы больше не следует из этой ветки обработки; фактическое поведение DOM должен подтвердить следующий автоматический браузерный запуск.

## Выполненные проверки

**10/10 PASS:** независимый [session-code-check.cjs](session-code-check.cjs) и [машиночитаемый протокол](session-code-review.json). Остальные проверки используют управляемые ответы транспорта для точного порядка событий. Временное хранилище удалено; токены и коды не записаны в протокол.
