# Критерии качества

**Статус:** предложено

Этот документ определяет минимальные проверки перед объединением изменений и выпуском версии. Цель — не дать игровому, методическому и техническому слоям расходиться.

## Проверка A — документация

- все внутренние Markdown-ссылки существуют;
- нет дублирующихся идентификаторов механик, задач и архитектурных решений;
- новый крупный модуль включён в `docs/README.md`;
- изменение архитектурной границы сопровождается архитектурным решением;
- новый термин не противоречит словарю и методическому профилю;
- пояснительный текст соответствует [`../LANGUAGE_POLICY.md`](../LANGUAGE_POLICY.md).

## Проверка B — схема учебного содержания

- JSON валиден;
- идентификаторы уникальны;
- все `source_id` существуют;
- `method_profile` существует;
- требуемые компетенции существуют;
- опубликованный пакет не изменён задним числом;
- правильный ответ не попадает в данные, отправляемые клиенту.

## Проверка C — методика

Для задания, которое попадёт в рейтинговый или экзаменационный режим:

- источник проверен;
- правильный ответ однозначен в выбранном методическом профиле;
- ложные варианты правдоподобны, но неверны по конкретной причине;
- объяснение раскрывает принцип, а не только сообщает ответ;
- российская нотация соблюдается там, где профиль требует В/Н, П/Р и другие отечественные обозначения;
- реальный случай имеет подтверждённое происхождение данных;
- результат независимо проверен методологом и метеорологическим верификатором, если меняется предметная истинность.

## Проверка D — игровая механика

- правильность важнее скорости;
- постоянная прокачка не даёт преимущества в рейтинговом режиме;
- задержки и блокировки имеют ограничение;
- одинаковый журнал событий приводит к одинаковому результату;
- поражение не отнимает постоянный учебный прогресс.

## Проверка E — сетевой режим

- сервер является авторитетным источником состояния;
- переподключение восстанавливает состояние;
- повторные и пришедшие не по порядку события обрабатываются корректно;
- зритель не видит ответ раньше закрытия задачи;
- воспроизведение матча приводит к тому же итоговому состоянию;
- клиентский таймер не может изменить серверный результат.

## Проверка F — пользовательский интерфейс

- во время активной задачи главный объект занимает доминирующую область;
- на мобильном устройстве действует принцип «одна задача — один фокус»;
- области нажатия имеют достаточный размер;
- смысл не передаётся только цветом;
- поддерживается режим уменьшенной анимации;
- метеорологические цвета не подменяются декоративной темой.

## Проверка G — доступность

- основные действия доступны с клавиатуры;
- видимы состояния фокуса;
- обеспечен читаемый контраст;
- обычные элементы интерфейса имеют подписи для средств экранного чтения;
- там, где цвет учебно значим, есть дополнительные смысловые маркеры.

## Проверка H — производительность

Перед пилотной эксплуатацией:

- бюджетный ноутбук и средний смартфон проходят основной сценарий;
- карта не блокирует основной поток заметными паузами;
- архивные материалы загружаются по мере необходимости;
- большое число зрителей проверено на аудиторию;
- переподключение испытано на нестабильной сети;
- живой мир имеет профили упрощения анимации;
- длительная работа большого экрана не приводит к накоплению памяти или падению частоты кадров.

## Проверка I — безопасность и приватность

- в клиентской части нет секретов;
- права проверяются сервером;
- административные действия журналируются;
- входные данные проверяются на границах API и WebSocket;
- публичные сетевые действия ограничены по частоте;
- камера, микрофон и геолокация пользователя не собираются без отдельной необходимости;
- короткий код входа используется только в допустимом профиле безопасности;
- внешние звуки и графические материалы имеют подтверждённые права использования.

## Проверка J — художественная целостность

- новый экран соответствует руководству по пиксельной графике;
- профессиональная карта остаётся главным объектом во время учебной задачи;
- метеорологические семантические цвета не изменены;
- новый графический ресурс разбивается на переиспользуемые элементы, если это возможно;
- фоновая анимация не мешает чтению;
- изменение принято арт-директором;
- насыщенная анимация дополнительно проверена специалистом по браузерной производительности.

## Условия готовности задачи к началу работы

Задача готова к разработке, если определены:

- проблема;
- границы работы;
- критерии приёмки;
- зависимости;
- методический профиль и источник для предметной задачи;
- визуальный эталон для пользовательского изменения;
- тестовый сценарий;
- исполнитель и независимые принимающие агенты.

## Условия завершения функции

Функция считается завершённой, если:

- код или учебное содержание реализованы;
- автоматические проверки проходят;
- документация обновлена;
- нужные технические показатели определены;
- нет открытых критических методических неоднозначностей;
- изменение совместимо с правилами воспроизведения и версионирования либо имеет отдельное решение о миграции;
- все обязательные независимые проверки из `agents/registry.yaml` завершены.
