# Архитектурные решения (ADR)

ADR фиксируют решения, которые влияют на несколько модулей или которые дорого отменять после реализации.

Аббревиатура ADR сохраняется как общепринятое имя формата файлов, но пояснительный текст оформляется по-русски.

## Принятые решения

- `ADR-0003-multi-agent-development-governance.md` — управление многоагентной разработкой и независимая приёмка.
- `ADR-0004-phaser-webgl-pixel-asset-pipeline.md` — Phaser 4/WebGL как runtime живого мира и воспроизводимый конвейер пиксельных ресурсов.

## Когда требуется архитектурное решение

- выбор модели авторитетного сервера;
- изменение границ программных пакетов;
- смена формата воспроизведения матча;
- новый принцип версионирования;
- изменение смысла методических профилей;
- выбор стратегии отображения карты;
- изменение правил хранения опубликованного учебного содержания;
- смена рейтинговой модели;
- существенное изменение модели безопасности или приватности;
- изменение основополагающих принципов продукта;
- изменение правил многоагентной приёмки;
- смена основного игрового runtime или renderer;
- смена канонического формата production asset/scene pipeline.

## Формат файла

Имена файлов сохраняются в техническом виде:

`ADR-XXXX-short-title.md`

Рекомендуемая структура документа:

```markdown
# ADR-XXXX — Название

Статус: предложено | принято | заменено | отклонено
Дата: ГГГГ-ММ-ДД

## Исходная ситуация
...

## Решение
...

## Последствия
### Положительные
- ...
### Отрицательные и стоимость
- ...

## Рассмотренные альтернативы
- ...

## Связанные материалы
- задача / запрос на объединение / документация
```

Если автоматические средства требуют машинные значения `proposed`, `accepted`, `superseded`, `rejected`, они хранятся отдельно от человекочитаемого текста.

## Правило

Архитектурное решение описывает **почему** принято решение. Текущая спецификация описывает **что** теперь считается правильным.

Если решение заменено новым, старый документ не удаляется: статус меняется на «заменено», а новый документ ссылается на него.
