# 06. Технические требования и архитектурные ограничения

## 1. Общий принцип

Проект строится как **браузерное адаптивное приложение**, пригодное для запуска:

- на обычном ноутбуке преподавателя;
- на компьютерах учебного класса;
- на смартфонах студентов;
- на проекторе или большом экране в зрительском режиме.

Для базового сценария не требуется установка отдельного настольного или мобильного приложения.

## 2. Зафиксированный стек первого рабочего среза

### Клиентская часть

- TypeScript;
- React — компонентная оболочка приложения, обычный интерфейс, формы, навигация и панели;
- Phaser 4 — игровой runtime живого пиксельного мира внутри `packages/world-engine`;
- WebGL — основной путь рендера живого мира через Phaser;
- CSS;
- Canvas/SVG для карт, станционных моделей и интерактивной метеорологической геометрии;
- PWA как необязательная возможность.

Phaser не заменяет React и не является источником метеорологической логики. `map-engine` остаётся отдельным специализированным SVG/Canvas-модулем: схемы станций, фронты, изобары, геометрические ответы и профессиональные подписи не переносятся в Phaser только ради единого способа рендера.

Версия Phaser и графических инструментов фиксируется в `config/art-toolchain.yaml`. Смена major-версии Phaser требует отдельного архитектурного решения или явного пересмотра `ADR-0004`.

### Серверная часть

- Node.js + TypeScript;
- REST/HTTP для учётных записей, учебного содержания и истории;
- WebSocket/Socket.IO для матчей в реальном времени;
- проверка схем данных на границах API.

### Хранение данных

Для локального прототипа допустим SQLite.

Для многопользовательской версии:

- PostgreSQL — основная база данных;
- Redis — присутствие пользователей, обмен сообщениями между процессами и координация матчей при масштабировании;
- объектное хранилище — изображения карт, архивные пакеты и крупные графические файлы.

Конкретный стек предметных и серверных модулей может меняться без изменения доменной логики. Выбор Phaser/WebGL для живого мира и контракт графических ресурсов зафиксированы отдельно в `ADR-0004` до явной замены этого решения.

## 3. Основные программные модули

```text
apps/
  web/                 # браузерный React-интерфейс игрока
  server/              # сервер
  display/             # автономный большой экран
  tools/               # служебные средства общего назначения
packages/
  game-rules/          # игровые правила
  content-schema/      # схема учебного содержания
  meteorology-domain/  # предметная метеорологическая модель
  realtime-protocol/   # протокол сетевых матчей
  world-engine/        # Phaser/WebGL runtime живого мира
  map-engine/          # профессиональная карта SVG/Canvas
  ui/                  # общие элементы интерфейса
  replay/              # воспроизведение журнала событий
content/
  method-profiles/     # методические профили
  packs/               # пакеты учебного содержания
  sources/             # источники
  scenarios/           # сценарии
assets/
  source/              # редактируемые исходники пиксель-арта
  scenes/              # Tiled JSON-сцены
  manifests/           # semantic IDs, pivots, animation/provenance metadata
  generated/           # производные runtime-ресурсы; ручная правка запрещена
tools/
  assets/              # sprite-tools / AssetPack integration
```

Технические имена каталогов сохраняются как программный контракт. В пояснительном тексте используются русские названия.

## 4. Предметный метеорологический модуль

Отдельный пакет содержит только предметную модель:

- наблюдение станции;
- абстракции кодов КН;
- слои карты;
- барические образования;
- фронты;
- уровни свободной атмосферы;
- идентификаторы терминологии;
- типы эталонных ответов.

Пользовательский интерфейс, Phaser/WebGL и игровой баланс в этот пакет не помещаются.

## 5. Игровые правила

Отдельный детерминированный пакет содержит:

- Надёжность;
- оперативный ресурс;
- игровые эффекты;
- серии правильных действий;
- временные ограничения между действиями;
- автомат состояний раунда;
- подсчёт результата.

По возможности один и тот же пакет используется на сервере и в тестах клиента, но окончательное решение всегда остаётся за сервером.

## 6. Модуль учебного содержания

Функции:

- загрузка версионируемых пакетов;
- проверка схемы;
- выбор методического профиля;
- формирование экземпляра задания;
- проверка ответа;
- хранение метаданных сложности;
- хранение происхождения и источников данных.

## 7. Модуль карт и графики

Требования:

- независимые слои;
- масштабирование и перемещение;
- наложения SVG/Canvas;
- линии фронтов;
- изобары и изаллобары;
- схемы нанесения станций;
- геометрические ответы;
- возможность показывать исходное изображение карты под векторными интерактивными слоями;
- отдельные варианты для настольного и мобильного устройства.

На первом этапе не требуется строить полноценную ГИС. Нужен специализированный учебный модуль картографической работы.

Профессиональная карта остаётся отдельной от Phaser/WebGL-сцены. Изменение этой границы требует отдельного архитектурного решения и методико-технической проверки.

## 8. Пользователи и роли

Технические роли:

- `student` — студент;
- `instructor` — преподаватель;
- `content_author` — автор учебного содержания;
- `method_reviewer` — методический проверяющий;
- `admin` — администратор;
- `display` — автономный большой экран.

Права обязательно проверяются сервером.

## 9. Группы и курсы

Основные сущности:

- учебное учреждение;
- курс;
- учебная группа;
- назначенное задание;
- турнир;
- профиль учебного содержания;
- правила оценивания.

Один пользователь может состоять в нескольких курсах.

## 10. Учёт прогресса

Отдельно хранятся:

- неизменяемый журнал попыток;
- агрегированная статистика;
- состояние освоения навыков;
- соревновательный рейтинг;
- достижения;
- оценка или экспорт результата курса.

Одна числовая величина `score` не используется для всех целей сразу.

## 11. Сервер матчей в реальном времени

Технический автомат состояний:

```text
CREATED
  ↓
LOBBY
  ↓
READY
  ↓
RUNNING
  ↓
ROUND_TRANSITION
  ↓
FINISHED
```

Дополнительные состояния:

- `PAUSED` — пауза в разрешённых режимах;
- `ABORTED` — принудительное завершение;
- `RECOVERING` — восстановление после сбоя.

Имена состояний остаются английскими как часть протокола.

## 12. Авторитетность сервера

На сервере обязательно выполняются:

- выбор или формирование задания;
- установка срока ответа;
- проверка результата;
- начисление игрового эффекта;
- изменение рейтинга;
- определение окончательного результата.

Состояние клиента считается только представлением серверного состояния. Phaser также является только визуальным runtime и не становится авторитетным источником результата матча.

## 13. Основы безопасности

- TLS;
- защищённые файлы cookie или безопасное хранение токенов;
- ограничения частоты запросов;
- проверка входных данных;
- защита от CSRF/XSS в соответствии с выбранной моделью входа;
- отсутствие секретов в клиентской сборке;
- серверная проверка прав;
- журнал административных действий;
- защищённые или неизменяемые идентификаторы версий опубликованных пакетов.

## 14. Приватность по умолчанию

Собираются только данные, необходимые для учебной и игровой функции.

По умолчанию не требуются:

- камера;
- микрофон;
- геолокация пользователя;
- телефонная книга;
- биометрия.

Для учебных организаций предусматривается удаление или архивирование данных по политике учреждения.

## 15. Доступность

Обязательно:

- клавиатурное управление;
- подписи для средств экранного чтения у обычных элементов интерфейса;
- настройка размера текста;
- запрет передачи смысла только цветом;
- дополнительные формы и символы для фронтов и статусов;
- режим повышенной контрастности;
- отсутствие опасных частых миганий;
- возможность уменьшить анимацию.

Цвета метеорологических карандашей сохраняются там, где это учебно значимо, но дополняются формой и легендой.

Режим уменьшенной анимации распространяется не только на CSS, но и на Phaser/living-world: фоновые tweens, частицы и частые ambient loops отключаются или упрощаются без потери учебного смысла.

## 16. Адаптивный интерфейс

### Настольный компьютер

- карта или задание доминирует;
- быстрые действия доступны без прокрутки;
- вторичные панели компактны.

### Мобильное устройство

- одна задача на экран;
- крупные области нажатия;
- горизонтальные списки навыков допустимы только вне активной задачи;
- карта имеет полноэкранный режим;
- состояние матча закреплено в компактной верхней полосе.

### Проектор и большой экран

- крупная типографика;
- минимум вторичного текста;
- приоритет зрительской читаемости;
- отсутствие элементов управления игрока.

Игровой canvas не определяет геометрию всего приложения: React-контейнер задаёт доступную область, а Phaser runtime реализует документированную стратегию logical pixel scaling и камеры.

## 17. Работа без сети и при плохом соединении

Одиночная тренировка может кэшировать:

- пакет учебного содержания;
- графические ресурсы;
- локальные попытки.

Рейтинговый сетевой матч требует соединения.

После восстановления сети локальные попытки синхронизируются по заранее заданным правилам разрешения конфликтов.

## 18. Испытания

### Модульные испытания

- игровые правила;
- декодеры и кодировщики;
- проверка учебного содержания;
- подсчёт результата;
- выбор методического профиля.

### Генеративные испытания свойств

- генераторы кодовых задач;
- эквивалентные соревновательные задания;
- сериализация воспроизведения матча;
- допустимые перестановки шагов.

### Интеграционные испытания

- REST;
- полный жизненный цикл WebSocket-матча;
- переподключение;
- публикация пакета учебного содержания;
- React ↔ Phaser mount/unmount без утечки game loop, listeners и runtime-ресурсов;
- восстановление/деградация при потере WebGL context там, где это возможно проверить.

### Сквозные испытания

- студент проходит одиночную смену;
- два игрока завершают дуэль;
- автоматический турнир проходит без ручного оператора;
- зритель подключается к активному матчу;
- воспроизведение приводит к тому же итоговому состоянию.

### Испытания графического конвейера

- схема `assets/manifests/asset-manifest.schema.json` валидирует production manifests;
- сохраняются animation tags, frame durations, pivots и interaction bounds;
- Tiled-сцены ссылаются на semantic asset IDs, а не на случайные координаты атласа;
- сборка воспроизводима из source + manifest + зафиксированного toolchain;
- отсутствуют atlas bleeding и случайное сглаживание пикселей;
- `assets/generated` не содержит ручных исправлений.

## 19. Автоматическая проверка учебного содержания

Каждое изменение учебного содержания должно запускать:

- проверку схемы;
- проверку ссылок на источники;
- поиск дублирующихся идентификаторов;
- проверку эталонных ответов;
- пробные запуски генераторов;
- проверку запрещённых обозначений для конкретного методического профиля;
- визуальное регрессионное испытание ключевых способов отображения заданий.

## 20. Техническая телеметрия и учебные события

Внутренние программные события могут иметь стабильные английские идентификаторы, например:

- `task_started`;
- `task_answered`;
- `hint_used`;
- `explanation_opened`;
- `match_started` / `match_finished`;
- `reconnect`;
- `replay_opened`;
- `content_error_reported`.

В пояснительной документации их смысл описывается по-русски.

Учебные события должны быть отделены от маркетинговой аналитики.

## 21. Бюджет производительности

Конкретные численные цели уточняются на этапе прототипа, но архитектурно требуется:

- быстрое первое взаимодействие;
- отсутствие тяжёлой обязательной трёхмерной сцены;
- отложенная загрузка архивных карт;
- оптимизированные SVG и растровые тайлы;
- устойчивость на бюджетных студенческих ноутбуках и средних смартфонах;
- отдельные режимы пониженной сложности анимации.

Для Phaser/WebGL дополнительно измеряются startup payload, CPU/GPU/texture memory, p50/p95 frame time, input latency, количество одновременно активных animated entities и длительная устойчивость projector/kiosk. Под нагрузкой первыми деградируют ambient layers, particles и редкие эффекты; учебный ввод, карта и таймер матча не деградируют первыми.

## 22. Границы API

Рекомендуемые технические области API:

```text
/auth
/courses
/content
/tasks
/progress
/matches
/tournaments
/replays
/leaderboards
/admin/content
```

Пути являются программным контрактом и не переводятся. Канал WebSocket отделяется от обычного REST-интерфейса.

## 23. Экспорт

Преподавателю необходимы:

- CSV/JSON результатов;
- отчёт по навыкам;
- журнал типичных ошибок;
- история турнира;
- ссылки или идентификаторы воспроизведения матчей.

Экспорт не должен содержать лишние персональные данные.

## 24. Условия готовности технического ядра

Ядро готово к пилотной эксплуатации, когда:

- пакет учебного содержания загружается и проверяется;
- не менее пяти типов заданий работают на настольном и мобильном устройстве;
- прогресс сохраняется;
- матч 1×1 устойчив к переподключению;
- зрительский режим работает;
- автономный большой экран самостоятельно показывает активные события;
- воспроизведение матча работает детерминированно;
- тесты игровых правил и учебного содержания выполняются автоматически;
- клиент не получает правильный ответ до его проверки сервером;
- базовый Phaser runtime проходит mount/unmount и performance-проверки;
- production asset pipeline воспроизводит хотя бы один проверенный atlas/scene packet из исходников без ручной правки generated-файлов.

## 25. Зафиксированный конвейер пиксельной графики

Основной редактор — Aseprite; Pixelorama — поддерживаемая открытая альтернатива. Канонический редактируемый формат спрайта — `.aseprite`. Канонический формат сцены — Tiled JSON (`.tmj/.tsj`); LDtk допускается для экспериментов до отдельного ADR.

```text
Aseprite / Pixelorama
        ↓
assets/source + assets/manifests
        ↓
sprite-tools: validation / tags / pivots / bounds / metadata
        ↓
Tiled: scene layers and interactables by semantic asset ID
        ↓
AssetPack: packing / optimisation
        ↓
assets/generated
        ↓
Phaser / WebGL
```

`assets/generated` запрещено править вручную. Ошибка исправляется в исходнике, manifest или pipeline и затем воспроизводимо пересобирается. Точные версии и политика обновления находятся в `config/art-toolchain.yaml`; подробности — в `docs/design/PIXEL_ASSET_PIPELINE.md` и `docs/architecture/GAME_RUNTIME_AND_ASSETS.md`.
