# 06. Технические требования и архитектурные ограничения

## 1. Общий принцип

Проект строится как **браузерное адаптивное приложение**, пригодное для запуска на ноутбуке преподавателя, компьютерах учебного класса, смартфонах студентов и проекторе/большом экране. Для базового сценария не требуется отдельное настольное или мобильное приложение.

Технологический выбор не должен разрушать доменные границы: учебная истина, игровые правила, визуальный runtime, карта и сетевой сервер остаются раздельными подсистемами.

## 2. Зафиксированный стек первого рабочего среза

### Клиентская часть

- TypeScript;
- React — оболочка приложения, обычный интерфейс, формы, навигация и панели;
- Phaser 4 — игровой runtime живого пиксельного мира внутри `packages/world-engine`;
- WebGL — основной путь рендера живого мира через Phaser, с предусмотренной деградацией там, где это поддерживает выбранный runtime;
- CSS — обычный интерфейс и адаптивность;
- SVG/Canvas — профессиональная метеорологическая геометрия и `map-engine`;
- PWA — необязательная возможность.

Phaser **не заменяет React** и **не является источником метеорологической логики**. `map-engine` не переводится в Phaser только ради единообразия рендера: схемы станций, фронты, изобары, геометрические ответы и подписи требуют собственного точного контракта SVG/Canvas.

Версия Phaser и графических инструментов фиксируется в `config/art-toolchain.yaml`; major-обновление Phaser требует отдельного архитектурного рассмотрения.

### Серверная часть

- Node.js + TypeScript;
- REST/HTTP для учётных записей, учебного содержания и истории;
- WebSocket/Socket.IO для матчей в реальном времени;
- проверка схем данных на границах API.

### Хранение данных

Для локального прототипа допустим SQLite. Для многопользовательской версии: PostgreSQL — основная база данных; Redis — присутствие пользователей, обмен сообщениями и координация матчей; объектное хранилище — изображения карт, архивные пакеты и крупные графические файлы.

## 3. Основные программные модули

```text
apps/
  web/                 # React-интерфейс игрока
  server/              # REST + сетевые матчи + авторитетное состояние
  display/             # автономный большой экран
  tools/               # общие служебные средства
packages/
  game-rules/          # игровые правила
  content-schema/      # схема учебного содержания
  meteorology-domain/  # предметная метеорологическая модель
  realtime-protocol/   # протокол сетевых матчей
  world-engine/        # Phaser/WebGL runtime живого мира
  map-engine/          # профессиональная карта SVG/Canvas
  ui/                  # общие элементы интерфейса
  replay/              # воспроизведение журнала событий
assets/
  source/              # редактируемый pixel-art source
  scenes/              # Tiled JSON (.tmj/.tsj)
  manifests/           # semantic IDs, pivots, animations, provenance
  generated/           # только сборочные runtime-артефакты
tools/
  assets/              # sprite-tools / AssetPack integration
```

Названия каталогов и пакетов остаются английскими как программный контракт.

## 4. Контракт графических ресурсов

Основной редактор пиксельной графики — Aseprite; Pixelorama поддерживается как свободная альтернатива. Канонический формат редактируемого спрайта — `.aseprite`. Канонический формат сцены — Tiled JSON (`.tmj/.tsj`). LDtk допускается только для явно обозначенных экспериментов, пока ADR не изменит основной формат.

Путь производства:

```text
Aseprite / Pixelorama
        ↓
assets/source + assets/manifests
        ↓
sprite-tools: проверка, animation tags, pivots, bounds, metadata
        ↓
Tiled: слои сцены и интерактивные объекты по semantic asset ID
        ↓
AssetPack: упаковка и web-оптимизация
        ↓
assets/generated
        ↓
Phaser loader / WebGL runtime
```

`assets/generated` запрещено править вручную. Ошибка исправляется в source/manifest/pipeline и затем воспроизводимо пересобирается. Схема базового asset manifest хранится в `assets/manifests/asset-manifest.schema.json`.

## 5. Предметный метеорологический модуль

Отдельный пакет содержит только предметную модель: наблюдение станции, абстракции кодов КН, слои карты, барические образования, фронты, уровни свободной атмосферы, идентификаторы терминологии и типы эталонных ответов. Пользовательский интерфейс, Phaser и игровой баланс в этот пакет не помещаются.

## 6. Игровые правила

Отдельный детерминированный пакет содержит Надёжность, оперативный ресурс, игровые эффекты, серии правильных действий, временные ограничения, автомат состояний раунда и подсчёт результата. Сервер остаётся окончательно авторитетным.

## 7. Модуль учебного содержания

Функции: загрузка версионируемых пакетов, проверка схемы, выбор методического профиля, формирование экземпляра задания, проверка ответа, сложность и происхождение/источники данных.

## 8. Модуль карт и графики

Требования: независимые слои; масштабирование/перемещение; SVG/Canvas overlays; линии фронтов; изобары/изаллобары; схемы станций; геометрические ответы; исходное изображение под интерактивными слоями; desktop/mobile variants.

На первом этапе не нужна полноценная ГИС. Нужен специализированный учебный картографический модуль. Его корректность и интерактивность не зависят от Phaser.

## 9. Игровой runtime и живой мир

`packages/world-engine` использует Phaser 4 и отвечает за: lifecycle игровой сцены, WebGL-конфигурацию, загрузку валидированных runtime-ресурсов, sprite animation playback, cameras, tweens, particles, filters/shaders и renderer diagnostics.

`living-world-engineer` задаёт состояние и поведение мира поверх этих primitives: время суток/сезон, seeded ambient schedules, NPC/fauna/interactables и профили плотности. Покадровое состояние не передаётся через React и не стримится с сервера.

Контракт пиксельного рендера: nearest-neighbour filtering, отсутствие случайного smoothing, осмысленная привязка к логической пиксельной сетке, независимость authored sprite FPS от display FPS, защита от atlas bleeding.

## 10. Пользователи и роли

Технические роли: `student`, `instructor`, `content_author`, `method_reviewer`, `admin`, `display`. Права обязательно проверяются сервером.

## 11. Группы и курсы

Основные сущности: учебное учреждение, курс, группа, назначенное задание, турнир, профиль содержания и правила оценивания. Один пользователь может состоять в нескольких курсах.

## 12. Учёт прогресса

Отдельно хранятся: неизменяемый журнал попыток, агрегированная статистика, состояние освоения навыков, соревновательный рейтинг, достижения и оценка/экспорт результата курса. Одна величина `score` не используется для всех целей.

## 13. Сервер матчей в реальном времени

```text
CREATED → LOBBY → READY → RUNNING → ROUND_TRANSITION → FINISHED
```

Дополнительные состояния: `PAUSED`, `ABORTED`, `RECOVERING`.

## 14. Авторитетность сервера

На сервере выполняются выбор/формирование задания, срок ответа, проверка результата, игровые эффекты, рейтинг и окончательный результат. Клиент — представление серверного состояния.

## 15. Основы безопасности

TLS; защищённые cookie/токены; rate limiting; проверка входных данных; CSRF/XSS-защита по модели входа; отсутствие секретов в клиентской сборке; серверная проверка прав; журнал административных действий; неизменяемые идентификаторы опубликованных версий.

## 16. Приватность по умолчанию

Собираются только необходимые данные. По умолчанию не нужны камера, микрофон, геолокация, телефонная книга и биометрия. Для учебных организаций предусматривается политика удаления/архивирования.

## 17. Доступность

Обязательны клавиатурное управление, подписи для средств экранного чтения у обычных элементов UI, настройка размера текста, отсутствие передачи смысла только цветом, формы/символы для фронтов и статусов, повышенная контрастность, отсутствие опасного мигания и уменьшение анимации.

`reduced-motion` должен менять не только CSS, но и профиль Phaser/living-world runtime: отключать/упрощать фоновые tweens, particles и частые ambient loops без потери смысла задания.

## 18. Адаптивный интерфейс

Desktop: карта/задача доминирует, основные действия без прокрутки. Mobile: одна задача на экран, крупные touch targets, полноэкранная карта. Projector/display: крупная типографика, минимум вторичного текста, отсутствие управления игрока.

Игровой canvas не должен определять размер приложения; React-контейнер задаёт доступную область, а runtime выбирает документированную стратегию logical pixel scaling/camera viewport.

## 19. Работа без сети и при плохом соединении

Одиночная тренировка может кэшировать пакет содержания, графические ресурсы и локальные попытки. Рейтинговый матч требует соединения. Синхронизация после восстановления сети следует заданным правилам конфликтов.

## 20. Производительность и устойчивость WebGL

Для animation-heavy PR фиксируются бюджеты desktop, mid-range mobile и projector/kiosk. Измеряются startup payload, CPU/GPU memory, p50/p95 frame time, input latency, число одновременно активных animated entities и длительная стабильность display-клиента.

Под нагрузкой первыми деградируют ambient layers/particles/rare effects. Учебный ввод, карта, таймер матча и профессиональные обозначения не деградируют первыми. Runtime должен учитывать visibility pause/throttle и восстановление после WebGL context loss.

## 21. Испытания

Модульные: игровые правила, кодеки, содержание, подсчёт результата, методические профили. Генеративные свойства: генераторы задач, эквивалентность, replay serialization. Интеграционные: REST, WebSocket lifecycle, reconnect, content publication, React↔Phaser mount/unmount. E2E: одиночная смена, дуэль, автономный турнир, spectator, replay.

Для графического контура отдельно проверяются: manifest schema, reproducible asset generation, сохранение animation tags/pivots, Tiled semantic IDs, atlas bleeding/sampling, reduced-motion и visual/runtime regression fixtures.

## 22. Автоматическая проверка учебного содержания

Каждое изменение содержания запускает schema validation, проверку источников, duplicate IDs, эталонные ответы, пробные генераторы, ограничения методического профиля и визуальные регрессионные испытания ключевых способов отображения.
