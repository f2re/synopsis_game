# 03. Онлайн PvP, батлы, трансляции и replay

## 1. Цель онлайн-слоя

Онлайн-режим должен превращать учебную работу в короткое живое соревнование, пригодное как для самостоятельной игры, так и для занятия в аудитории.

Основные сценарии:

- 1v1 между студентами;
- 2v2 и 3v3;
- массовый блиц;
- турнир учебной группы;
- преподавательский показ на проекторе;
- spectator mode;
- replay и разбор матча.

## 2. Модель матча

Сервер является авторитетным источником состояния.

Клиент отвечает только за:

- визуализацию;
- ввод ответа;
- локальную анимацию;
- предварительный UX таймера.

Сервер отвечает за:

- генерацию/выбор задания;
- проверку ответа;
- таймер;
- OR;
- эффекты;
- Надёжность;
- рейтинг;
- завершение раунда;
- event log.

## 3. Событийная модель

Минимальный набор событий:

```text
MATCH_CREATED
PLAYER_JOINED
MATCH_READY
MATCH_START
ROUND_START
TASK_START
ANSWER_SUBMITTED
ANSWER_ACCEPTED
ANSWER_REJECTED
TASK_RESULT
RESOURCE_CHANGED
ABILITY_USED
EFFECT_APPLIED
SHIELD_APPLIED
PARRY
COUNTER
COMBO_CHANGED
RELIABILITY_CHANGED
ROUND_END
MATCH_END
PLAYER_DISCONNECTED
PLAYER_RECONNECTED
```

Все события имеют server timestamp и sequence number.

## 4. WebSocket-транспорт

Базовая схема:

```text
Player A ─┐
          ├── WebSocket ── Match Server ── Event Store
Player B ─┘                    │
                              ├── Spectators
                              ├── Instructor view
                              └── Replay renderer
```

Для MVP допустим Socket.IO. В дальнейшем можно перейти на чистый WebSocket-протокол без изменения доменной модели.

## 5. Почему не нужна видеотрансляция

Для наблюдения за матчем сервер передаёт **состояние и события**, а не видео.

Преимущества:

- низкий трафик;
- один матч может смотреть большая аудитория;
- spectator UI может отличаться от player UI;
- легко строить replay;
- преподаватель видит методические метрики, которых нет в видеопотоке;
- можно переключать язык/масштаб интерфейса у зрителя независимо от игроков.

WebRTC нужен только для будущего голоса/камеры, но не для ядра игры.

## 6. Spectator mode

Зритель не должен видеть правильный ответ до фиксации ответов игроков.

Зритель видит:

- карту/ситуацию;
- текущую категорию задачи;
- Надёжность игроков;
- OR;
- серию;
- применённые действия;
- точность;
- позицию в матче;
- последние события.

Опционально после закрытия вопроса показывается правильное решение и краткое пояснение.

## 7. Instructor mode

Преподаватель имеет расширенный интерфейс:

- ответы обоих игроков;
- время ответа;
- тип ошибки;
- mastery по теме;
- latency;
- цепочку действий;
- классификацию нарушения методики;
- кнопку «пометить момент для разбора»;
- паузу в нерейтинговом учебном матче;
- принудительный переход к разбору после завершения.

Instructor mode не должен позволять менять исход рейтингового матча после его старта.

## 8. Турнир учебной группы

Преподаватель создаёт комнату и получает код/QR.

Настройки:

- профиль курса;
- список тем;
- режим;
- длительность раунда;
- число участников;
- seed policy;
- одинаковые или эквивалентные задания;
- наличие spectator screen;
- тренировочный/рейтинговый статус.

Поддерживаемые схемы:

- single elimination;
- double elimination — позже;
- round robin;
- swiss — позже;
- mass qualifier + playoff.

## 9. Mass qualifier

Для занятия с большой группой:

1. все участники получают синхронные или эквивалентные задания;
2. проводится N коротких раундов;
3. система строит промежуточную таблицу;
4. top-8/top-4 переходят в playoff;
5. главный матч автоматически выводится на projector view.

## 10. Mirror и Equivalent режимы

### Mirror

Оба игрока получают одно и то же задание.

Плюсы: максимальная прозрачность.

Минусы: проще подсмотреть ответ, выше риск синхронного копирования.

### Equivalent

Игроки получают разные данные одинаковой сложности.

Пример:

- тема у обоих: температура из КН-01;
- коды разные;
- формат одинаковый;
- эмпирическая сложность близкая.

Для Ranked рекомендуется `Equivalent`, для демонстрационного финала — возможно `Mirror`.

## 11. Синхронизация таймеров

Каждая задача получает:

- `server_started_at`;
- `deadline_at`;
- `grace_window_ms`;
- `sequence`.

Клиент отображает локальный таймер, но решение о сроке принимает сервер.

## 12. Переподключение

Требования:

- короткое отключение не должно немедленно завершать матч;
- клиент может запросить snapshot;
- сервер присылает текущий state + sequence;
- пропущенные события восстанавливаются по event log;
- после превышения disconnect policy применяется техническое поражение/бот/заморозка в зависимости от режима.

## 13. Replay

Replay хранится как детерминированный или квазидетерминированный журнал событий, а не как видео.

Пример записи:

```json
{
  "seq": 153,
  "time_ms": 36420,
  "player_id": "p1",
  "event": "TASK_RESULT",
  "task_instance_id": "x7823",
  "correct": true,
  "duration_ms": 4820,
  "effect": "QUICK_HIT",
  "value": 6
}
```

Для воспроизведения хранятся:

- версия правил;
- версия content pack;
- seed;
- task instance data;
- события;
- профиль методики;
- версия баланса.

## 14. Разбор после матча

Post-match экран должен быть методическим, а не только соревновательным.

Показывать:

- результат;
- точность;
- среднее и медианное время;
- 3 самые дорогие ошибки;
- нарушенные принципы;
- темы для повторения;
- replay markers;
- сравнение с собственной предыдущей статистикой.

## 15. Античит

### Обязательные правила

- правильный ответ не отправляется клиенту до завершения задачи;
- task instance подписывается/идентифицируется сервером;
- проверка выполняется сервером;
- эффекты рассчитываются сервером;
- рейтинг обновляется сервером;
- клиент не выбирает seed;
- подозрительные паттерны логируются.

### Дополнительные сигналы

- невозможные времена ответа;
- повторяемость идентичных паттернов;
- частая смена клиентов/сессий;
- несоответствие input events и submit;
- аномальный win-rate по конкретному набору задач.

Античит не должен превращаться в агрессивный сбор личных данных.

## 16. Приватность

Для студенческого курса по умолчанию хранить минимум:

- идентификатор пользователя;
- отображаемое имя/ник;
- группа;
- игровые/учебные результаты;
- события матчей;
- техническую диагностику в разумном объёме.

Не требовать камеру/микрофон для участия.

## 17. Наблюдаемость сервера

Метрики:

- active matches;
- connected players;
- spectators;
- event lag;
- p50/p95 round-trip latency;
- task validation latency;
- reconnect rate;
- match completion rate;
- answer distribution;
- content errors.

## 18. Fail-safe

Если контент-сервис недоступен во время уже начатого матча:

- матч использует заранее подготовленный набор task instances;
- сервер не должен зависеть от внешнего API на каждый вопрос;
- результаты записываются локально/в очередь;
- рейтинг подтверждается после успешной фиксации транзакции.

## 19. Масштабирование

MVP:

- один application server;
- Socket.IO/WebSocket;
- PostgreSQL или SQLite для локального пилота;
- event log в БД.

Дальше:

- stateless API;
- отдельные match workers;
- Redis для presence/pub-sub;
- PostgreSQL;
- объектное хранилище для карт/архивов;
- CDN для статических ассетов.

## 20. Acceptance criteria онлайн-MVP

Онлайн-ядро считается готовым, если:

- два браузера могут завершить 1v1 без рассинхронизации;
- сервер авторитетно проверяет ответы;
- зритель подключается в середине матча;
- replay воспроизводит тот же итог;
- reconnect возвращает игрока в актуальное состояние;
- преподаватель может создать комнату и запустить турнир;
- задержка клиента не позволяет изменить результат через подмену локального таймера.
