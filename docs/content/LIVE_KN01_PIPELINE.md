# Поток обработки актуальных КН-01 — реальные станции и автоматическое формирование заданий

**Статус:** принятая концепция

## 1. Цель

КН-01 в игре должен работать не только на статическом банке вопросов, но и на **актуальных метеорологических телеграммах реальных станций**. Из входного потока система автоматически формирует проверяемые упражнения на кодирование, дешифрирование, нанесение станции и критику наблюдений.

Преподаватель не должен вручную создавать эталонные ответы или оценивать результат.

## 2. Базовый поток обработки

```text
Источник данных
   ↓
Адаптер приёма
   ↓
Хранилище исходных телеграмм
   ↓
Удаление дублей / проверка времени / определение станции
   ↓
Декодер КН-01
   ↓
Каноническое наблюдение
   ↓
Проверка и контроль качества
   ↓
Генератор заданий
   ↓
Экземпляр задания
   ↓
Серверная проверка ответа
   ↓
Одиночная игра / Блиц / сетевой матч / большой экран
```

## 3. Источники входных данных

Подключение выполняется через адаптеры. Ядро не должно зависеть от одного канала.

Минимально предусматриваются:

- `file-spool` — папка, куда поступают текстовые метеотелеграммы;
- `batch-file` — пакетный импорт архива файлов;
- `tcp-socket` — поток по TCP;
- `websocket-feed` — поток WebSocket;
- `unix-socket` — локальная интеграция при необходимости;
- `message-queue` — очередь сообщений для более крупного развёртывания;
- `manual-test-fixture` — тестовые входные данные только для разработки.

Это технические имена адаптеров. Термин «телеграмма» здесь означает метеорологическое кодовое сообщение, а не приложение Telegram.

## 4. Принцип сохранения исходного сообщения

Сырая входная телеграмма сохраняется неизменённой вместе с метаданными:

```json
{
  "raw_id": "...",
  "received_at": "...",
  "source_adapter": "file-spool",
  "source_name": "local-kn01-feed",
  "payload": "...",
  "checksum": "..."
}
```

Это позволяет:

- повторно разобрать сообщение новой версией декодера;
- расследовать ошибки;
- воспроизводить старые задания;
- не терять исходный материал.

## 5. Реестр станций

Система должна иметь реестр станций:

- идентификатор;
- WMO или локальный номер в соответствии с профилем;
- название;
- координаты;
- высоту;
- признак активности;
- допустимые псевдонимы;
- регион или группу для фильтрации.

Если станцию невозможно определить однозначно, сообщение помещается в карантин и не используется в рейтинговом режиме.

## 6. Набор правил и актуальность КН-01

Декодер и кодировщик всегда работают с явным `kn01_ruleset_id`.

Пример:

```text
KN01_CURRENT_RU_2026
KN01_LEGACY_TRAINING_1
```

Конкретная версия связывается с источником нормативной или методической документации и датой действия.

Нельзя:

- встраивать правила КН-01 жёстко в пользовательский интерфейс;
- молча менять набор правил для уже созданного воспроизведения матча;
- смешивать старые и действующие правила без явной маркировки.

## 7. Каноническое наблюдение

После разбора телеграмма преобразуется в предметную модель, например:

```json
{
  "station_id": "...",
  "observation_time": "...",
  "temperature_c": 2.3,
  "dewpoint_c": 1.7,
  "pressure_hpa": 1001.8,
  "wind_dir_deg": 240,
  "wind_speed": 6,
  "visibility": 8000,
  "ww": 61,
  "clouds": {},
  "source_raw_id": "...",
  "ruleset_id": "KN01_CURRENT_RU_2026"
}
```

Точный набор полей определяется предметным модулем `meteorology-domain`.

## 8. Автоматическая проверка

### Дешифрирование

`исходный КН-01 → каноническое наблюдение`.

Ожидаемый ответ формируется декодером.

### Кодирование

`каноническое наблюдение → группа или телеграмма КН-01`.

Проверка выполняется кодировщиком по тому же набору правил.

### Проверка обратного преобразования

Для допустимых сообщений должен выполняться контролируемый цикл:

```text
parse(encode(observation)) ≈ observation
```

Здесь технические имена функций сохранены как часть программного контракта. Допускаются только заранее определённые потери точности или формата конкретного кода.

### Схема нанесения станции

Схема строится из канонического наблюдения и проверяется по отдельным полям.

### Критика наблюдений

Система может автоматически сравнивать:

- внутреннюю согласованность одного наблюдения;
- соседние станции;
- временную последовательность;
- физические ограничения;
- правила кодирования.

Автоматическая критика должна хранить степень уверенности и тип правила. Эвристика не должна выдаваться за доказанную ошибку.

## 9. Политика актуальности данных

Для задач на текущих данных хранятся:

- `observation_time` — срок наблюдения;
- `received_at` — время получения;
- `freshness_class` — класс свежести;
- `is_delayed` — признак задержки;
- `is_retransmission` — признак повторной передачи.

Пример машинных классов:

- `live` — текущие;
- `recent` — недавние;
- `stale` — устаревшие;
- `archive` — архивные.

Рейтинговый режим использует только разрешённые классы.

## 10. Удаление дублей

Дубликаты определяются по сочетанию:

- станции;
- срока наблюдения;
- типа кода;
- контрольной суммы исходного сообщения или нормализованного содержимого.

Повторная доставка одной телеграммы не должна создавать бесконечную серию одинаковых заданий.

## 11. Карантин

Сообщение не попадает в игровой набор, если:

- декодер завершился ошибкой;
- станция неизвестна;
- группа неоднозначна;
- версия правил не соответствует данным;
- обнаружена критическая внутренняя несогласованность;
- время сообщения выходит за допустимое окно;
- данные повреждены.

Карантин доступен администратору и методисту для диагностики, но ручная обработка карантина не должна быть условием продолжения игры.

## 12. Автоматическое формирование заданий

Из одного наблюдения могут создаваться разные задания:

- дешифрировать температуру;
- дешифрировать давление;
- определить ветер;
- восстановить сокращённое давление;
- выбрать `ww`;
- собрать часть схемы станции;
- собрать полную схему станции;
- закодировать одну группу;
- закодировать телеграмму;
- найти ошибку в намеренно изменённой копии;
- сравнить две соседние станции;
- сравнить последовательные сроки.

## 13. Равенство условий в сетевом матче

В режиме эквивалентных заданий игроки могут получать разные актуальные наблюдения, но генератор нормализует:

- число операций;
- тип группы;
- число неоднозначных символов;
- длину ответа;
- фактическую статистическую сложность.

Если эквивалентность обеспечить нельзя, матч использует одну и ту же задачу или заранее откалиброванный фиксированный набор.

## 14. Зафиксированный снимок данных

Матч не должен зависеть от внешнего потока в момент каждого вопроса.

Сервис периодически строит фиксированный пакет:

```text
входной поток → проверенные наблюдения → снимок данных → набор заданий
```

Матч получает конкретную версию снимка, поэтому его можно точно воспроизвести после завершения.

## 15. Резервная цепочка

Если поток актуальных данных пропал:

1. используются свежие проверенные снимки;
2. затем последний недавний кэш;
3. затем проверенный архивный пакет;
4. интерфейс честно показывает происхождение и свежесть, если это существенно для режима.

Игра не должна останавливаться из-за временного отсутствия внешнего канала.

## 16. Автономность

Конвейер актуальных КН-01 самостоятельно выполняет:

- приём данных;
- синтаксический разбор;
- проверку;
- формирование заданий;
- формирование эталонных ответов;
- публикацию в набор доступных заданий;
- сбор технических показателей;
- помещение проблемных сообщений в карантин.

Роль преподавателя — не ручная проверка, а при необходимости просмотр статистики и проблемных случаев.

## 17. Наблюдаемость

Основные показатели:

- сообщений в минуту;
- доля успешного разбора;
- покрытие станций;
- доля дублей;
- доля карантина;
- распределение возраста данных;
- число сформированных заданий в минуту;
- ошибки проверки ответов;
- распределение версий набора правил.

## 18. Безопасность входного потока

Любой внешний поток считается недоверенным.

Обязательно:

- ограничение размера сообщений;
- проверка кодировки;
- очистка и проверка входных данных;
- запрет исполнения кода из содержимого телеграммы;
- аутентификация адаптера там, где источник сетевой;
- журналирование происхождения;
- ограничение частоты и управление переполнением очереди.

## 19. Метеорологическая приёмка

Изменение декодера, кодировщика, набора правил или логики формирования правильного ответа проходит две независимые проверки:

1. методолог российской синоптической школы подтверждает трактовку по источникам;
2. независимый метеорологический верификатор повторно выводит ожидаемый результат.

Расхождение блокирует публикацию задания в рейтинговом или экзаменационном режиме.

## 20. Критерии готовности

- [ ] файл с КН-01 автоматически создаёт проверяемые экземпляры заданий;
- [ ] сетевой источник работает через тот же конвейер без изменения игрового движка;
- [ ] декодер и кодировщик имеют версионируемый набор правил;
- [ ] дешифрирование и кодирование проверяются автоматически;
- [ ] исходное сообщение сохраняется;
- [ ] дубликаты не размножают задания;
- [ ] повреждённые сообщения уходят в карантин;
- [ ] актуальный поток можно заменить снимком или архивом без остановки игры;
- [ ] воспроизведение матча содержит версию снимка и набора правил;
- [ ] преподаватель не нужен для проверки ответа;
- [ ] методическая и независимая метеорологическая приёмка обязательны для изменения правильного ответа.
