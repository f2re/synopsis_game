# 09. Политика источников и методической верификации

## 1. Зачем это нужно

Для «Синоптического центра» недостаточно, чтобы ответ выглядел правдоподобно. Учебное правило должно быть:

- прослеживаемым до источника;
- привязанным к редакции/году;
- отделённым от игровых условностей;
- отделённым от локальной кафедральной методики;
- воспроизводимым в старых replay.

## 2. Классы авторитетности

### A — `official_current`

Действующий нормативный/методический документ Росгидромета, Гидрометцентра России или другого уполномоченного органа.

Используется для утверждений вида «в актуальной оперативной практике/нормативе».

### B — `classic_textbook`

Фундаментальный отечественный учебник.

Используется для понятий, классического синоптического метода, исторически сложившихся приёмов.

### C — `university_practicum`

Практикум/учебное пособие профильного вуза.

Используется для технологии выполнения учебных операций.

### D — `department_custom`

Методика кафедры/преподавателя.

Допустима, если явно названа и не выдаётся за общий норматив.

### E — `project_assumption`

Проектное решение команды игры.

Не может использоваться как источник метеорологического знания.

## 3. Правило конфликта источников

Если классический учебник и действующий норматив расходятся:

- не «исправлять» один другим молча;
- создать два method profile или versioned rule;
- в современном оперативном режиме приоритет у актуального официального документа;
- в историческом/учебном режиме возможно использование классической редакции с явной маркировкой.

## 4. Основные источники, уже подтверждённые при формировании концепции

### 4.1. А. С. Зверев, «Синоптическая метеорология», 1977

Классический источник для:

- определения синоптического метода;
- структуры первичного анализа;
- понятия подъёма карты;
- критики данных;
- исторической последовательности;
- правила ведущего потока;
- схемы ПЭСМ.

Доступная электронная копия, использованная для проектной сверки:

https://djvu.online/file/xhZZFjpf3uPUm

Перед формальным релизом следует использовать проверенный библиографический экземпляр/скан и зафиксировать страницы для каждого правила.

### 4.2. Методический кабинет Гидрометцентра России

Официальная страница нормативных и методических документов:

https://method.meteorf.ru/norma/norma.html

На странице опубликованы, в частности:

- РД 52.27.724-2019 «Наставление по краткосрочным прогнозам погоды общего назначения»;
- РД 52.27.723-2009 «Базовые требования к технологии подготовки краткосрочных прогнозов погоды»;
- методические материалы по ДМРЛ-С;
- КН-01 SYNOP;
- другие специализированные руководства.

Для production-контента необходимо сохранять точную редакцию/дату документа, а не ссылаться только на каталог.

### 4.3. КН-01 SYNOP

На официальной странице Методического кабинета опубликован «Код для оперативной передачи данных приземных метеорологических наблюдений с сети станций Росгидромета (КН-01 SYNOP)».

В source registry нужно хранить:

- точное название;
- редакцию;
- дату загрузки/проверки;
- локальный hash разрешённой копии или иной устойчивый идентификатор;
- область применения.

### 4.4. РГГМУ — практикум по синоптической метеорологии

В библиографическое ядро включается «Практикум по синоптической метеорологии» под ред. В. И. Воробьёва (РГГМУ/Гидрометеоиздат в соответствующей используемой редакции).

До публикации заданий на его основе необходимо занести конкретное издание в registry и указать страницы/разделы.

### 4.5. С. П. Хромов, В. И. Воробьёв, Н. А. Дашко и другие отечественные источники

Используются как элементы российской синоптической школы и учебного курса. Для каждого правила требуется конкретная запись `Source`; фамилия автора без произведения/редакции недостаточна.

## 5. Current-document check

Поскольку нормативы меняются, перед выпуском каждого major content pack выполняется проверка:

- не появилась ли новая редакция РД;
- актуален ли КН;
- не заменён ли документ;
- не изменились ли критерии ОЯ;
- не обновились ли методики МРЛ/спутникового анализа;
- не изменена ли терминология.

Результат проверки фиксируется датой.

## 7. Source requirement для TaskDefinition

Эталонное задание обязано иметь минимум один источник, кроме чисто технических/tutorial UI заданий.

```json
"sources": [
  {
    "source_id": "ZVEREV_1977",
    "locator": "chapter_3_section_3_4"
  }
]
```

## 8. Что считается «проверено»

Статусы:

- `draft` — автор подготовил задание;
- `source_checked` — ссылка на источник подтверждена;
- `method_reviewed` — проверено методистом;
- `pilot_validated` — прошло студенческий пилот без существенной неоднозначности;
- `published` — включено в release content pack;
- `deprecated` — больше не выдаётся новым игрокам;
- `revoked` — обнаружена содержательная ошибка.

## 9. Требование к спорным численным правилам

Любой коэффициент, порог или шаг, который может зависеть от:

- типа карты;
- редакции методики;
- региона;
- сезона;
- прогностического метода;
- кафедры,

хранится в контенте/профиле с источником.

Запрещено прошивать такие значения в универсальный код движка.

## 10. Реальные архивные данные

Для каждого сценария хранить provenance:

- поставщик;
- дата/срок;
- станционная/модельная/спутниковая природа данных;
- преобразования;
- лицензия/право использования;
- checksum исходного файла;
- описание preprocessing.

Если изображение карты вручную размечено для игры, исходник и слой разметки хранятся отдельно.

## 11. Синтетические задания

Разрешены для drills, если:

- физические величины валидны;
- генератор протестирован;
- задача не выдаётся за реальное наблюдение;
- `data_origin = synthetic_drill`;
- синтетика не используется для доказательства реальной метеорологической закономерности.

## 12. Требование к AI-generated контенту

LLM/генератор может:

- предложить формулировку;
- создать distractor draft;
- разметить текст;
- помочь сформировать JSON.

Но AI-generated правильный ответ **не публикуется без детерминированной проверки или методической рецензии**.

Для карт и сложной физики обязателен экспертный review.

## 13. Цитирование внутри игры

Студенту не нужно показывать библиографию после каждого блиц-вопроса.

Но из объяснения должна быть доступна кнопка/ссылка «Источник», открывающая:

- название документа/учебника;
- раздел;
- редакцию;
- статус профиля.

## 14. Проверка терминологии в CI

Для профиля `RUS_CLASSIC_*` автоматические lint-правила могут выявлять:

- `L/H` вместо В/Н в эталонном русском учебном слое;
- использование «подъём карты» как синонима всего анализа;
- конфликтующие версии одного rule ID;
- отсутствие источника;
- устаревший source status.

Lint не заменяет методиста.

## 15. Методический совет проекта

Перед production-релизом рекомендуется иметь минимум два независимых reviewer-уровня:

1. предметный специалист/преподаватель синоптической метеорологии;
2. автор/редактор учебного контента, проверяющий формулировку и однозначность.

Для спорного вопроса в Ranked лучше временно исключить задание, чем решать спор «по большинству игроков».

## 16. Золотое правило

Если команда не может ответить на вопрос:

> «Из какого источника, какой редакции и по какому методическому профилю это считается правильным?»

такое задание не должно попадать в рейтинговый или экзаменационный контент.
