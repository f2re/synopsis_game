# game-qa-automation

## When to use

Use for browser and integration game regression plans, Playwright E2E tests, defect reproduction and accountable release evidence. Avoid substituting this for a separate security, meteorology, performance or art approval.

## Procedure

1. Record exact SHA, branch, browser/device and flags; inspect apps/web/e2e, apps/web/e2e/visual and CI before test execution.
2. Cover KN-01 answers, roster access, Hub, mobile/projector, WebGL fallback, multiplayer reconnect, user privacy and reduced motion by risk.
3. Tag tests PASS, FAIL, BLOCKED, NOT_APPLICABLE or NOT_RUN; H3D in main is not applicable while its files remain in PRs.
4. Capture exact command, exit status, expected vs actual, screenshot/trace and independent retest; avoid fabricated QA evidence.

## Evidence and acceptance

Record branch and exact commit, files touched, executed commands, observed outputs, unanswered cases, review decisions and next required reviewer (integration-release-engineer and independent UX/performance reviewers). Never treat source citations or static checks as live test runs. The internal agents/registry.yaml and AGENTS.md govern the project, not external templates. No automatic remote installation is authorized.
